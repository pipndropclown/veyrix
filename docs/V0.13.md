# Veyrix V0.13 — Durable Research Store & Fast Research API

Veyrix remains paper-trading and historical simulation only. No wallets, private keys, exchange orders, blockchain transactions, leverage, margin, short selling, or real funds are involved.

## ResearchStore architecture

`ResearchStore` is vendor-neutral and implements `get`, `put`, `delete`, `has`, and capped `list`. The lookup path is:

1. Validate and normalize the requested research configuration.
2. Check the process-local memory store.
3. Check the configured research store.
4. Validate a store hit, hydrate memory, and return `STORE_HIT`.
5. Reuse an identical in-flight job when present.
6. Compute once, validate the complete record, populate memory, and attempt persistence.

Typed access statuses are `MEMORY_HIT`, `STORE_HIT`, `COMPUTED`, and `IN_FLIGHT_REUSED`. Persistence is reported separately as `PERSISTED`, `MEMORY_ONLY`, or `STORE_WRITE_FAILED`.

## Active stores and deployment

Memory is always available and requires no account or paid infrastructure. A filesystem adapter is enabled automatically in development or explicitly with:

```text
VEYRIX_RESEARCH_STORE=filesystem
VEYRIX_RESEARCH_STORE_PATH=<optional server-side directory>
```

No browser bundle receives these values. No external vendor was added: the current dependency and deployment model had no provider-neutral, guaranteed-free durable service that could be integrated without imposing an account or new infrastructure. Filesystem storage is durable on a persistent Node host, but Vercel/serverless filesystems may be ephemeral. The system status reports this adapter honestly and the application falls back to memory if it is absent or fails.

## Stored record (`veyrix-store-v1`)

Each record contains the run ID, creation/expiry dates, canonical configuration, reproducibility manifest, dataset and result fingerprints, compact summary, detailed result, performance timings, serialized-size metadata, pin state, and optional note. V0.12 `veyrix-cache-v1` exports remain verifiable but are not silently promoted into V0.13 store records; incompatible cache entries cause recomputation.

Integrity validation checks schema, run/manifest identity, dataset/manifest identity, a recomputed detailed-result fingerprint, both fingerprint prefixes, timestamps, required size fields, pin type, and note length. Corrupt or unsupported records are ignored. Read failure falls back to computation; write failure returns the valid result as `STORE_WRITE_FAILED` and retains it in memory.

## Compact summary

`veyrix-summary-v1` includes run/date/timeframe/anchor/mode, strategy set, top strategy, Temporal Research Score, Research Score, Multi-Regime Robustness, Anchor Consistency, Temporal Reliability, average OOS return, matched-benchmark beat rate, validation confidence, fingerprint prefixes, execution duration, access/persistence status, pin/note metadata, and response sizes. Metrics that do not apply to a single-anchor arena remain typed `null`; no statistics are fabricated.

The summary contains no strategy fold arrays, trade arrays, equity curves, or detailed validation results. Serialized byte counts cover summary, detailed result, and stored record. Non-finite values are normalized to `null` before persistence and response serialization.

## API routes

- `POST /api/research/run` — resolve or compute research and return status plus compact summary only.
- `GET /api/research` — newest-first summaries and deployment/store status; maximum 25.
- `POST /api/research` — compare two or three saved summaries without recomputation.
- `GET /api/research/:runId/summary` — summary only.
- `GET /api/research/:runId` — full stored record for details or deterministic JSON export.
- `PATCH /api/research/:runId` — update pin state and/or note when durable pinning is available.

The legacy validation API remains compatible, but new normal dashboard interactions use the compact research API.

## Research library, pinning, and notes

The library merges memory and store indexes by run ID, sorts newest first, and returns at most 25 summaries. It supports summary/detail views, JSON export, and comparison of two or three saved summaries. Comparison never reruns research.

Pinning is manual and only enabled for a configured adapter that supports persistence. Pinned records bypass ordinary expiry checks; memory-only pinning is not presented as durable. Notes are trimmed plain metadata with a 160-character maximum and do not participate in research identity. React escapes note display, and notes are never executed.

## Size and performance behavior

Run requests no longer return the giant detailed arena. The summary endpoint and library operate on compact metadata; detailed results cross the network only for explicit VIEW DETAILS or EXPORT actions. Multi-anchor API results retain only per-anchor summaries rather than repeating complete arenas. Cold computation remains inherently expensive, while memory and store hits avoid recomputation.

## Known limitations

The filesystem adapter is not shared across serverless instances and may be evicted on ephemeral deployments. There is no bundled cloud KV/database adapter. The filesystem index scans a capped local directory rather than using a database index. Large detail/export requests remain large by design. Existing synchronous research computation can block one Node process during cold analysis. Historical simulations, overlapping anchors, heuristic regimes, OHLC ambiguity, and incomplete real-execution modeling remain limitations; historical results do not predict future performance.
