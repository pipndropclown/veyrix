# Veyrix V0.14 — Normalized Research Artifacts

Veyrix remains a paper-trading and historical-simulation application. V0.14 changes research persistence and delivery only; strategy and execution behavior are unchanged.

## Size audit

The V0.13 extended-validation arena repeatedly embedded selected in-sample backtests in folds and then embedded complete strategy reports again in three ranking lists. The largest measured sections of a representative result were validation methods/folds (about 62.7 MB), selected in-sample analytics (about 62.1 MB when counted through their containing paths), equity curves (about 37.2 MB), drawdown curves (about 26.4 MB), and multi-regime output (about 28.4 MB). These figures overlap because the profiler measures each subtree; they identify duplication sources rather than additive totals.

## Store schema and artifacts

`veyrix-store-v2` separates run metadata from a content-addressed artifact dictionary. The metadata contains the manifest, compact summary, STANDARD view, artifact index, fingerprints, timings, and size metadata. Artifact categories are validation folds (`FD`), backtests (`BT`), equity curves (`EQ`), drawdown curves (`DD`), trades (`TR`), benchmarks (`BM`), sensitivity data (`SN`), shared configuration (`CF`), and regime/ranking data (`RG`).

An artifact ID is its category prefix plus the full SHA-256 hash of canonical, key-sorted content. Identical artifacts within a run share one entry. Curves use compact tuples and trade sets are separate artifacts. Ranking views retain IDs and scalar metrics rather than complete strategy reports. Non-selected sensitivity combinations persist parameters and scoring metrics, not temporary backtest internals; selected configurations retain their inspectable artifacts. This is the explicit boundary between transient computation data and persisted research evidence.

The filesystem layout is:

```text
.veyrix-research-v2/
  VRX-<run>/
    record.json
    artifacts/
      EQ-<hash>.json
      FD-<hash>.json
      ...
```

Artifacts are scoped to a run in V0.14, avoiding cross-run reference counting. Writes build a temporary run directory, write artifacts first and metadata last, then rename it into place. Cleanup removes the whole directory of an expired, unpinned run. IDs are strictly validated before filesystem path construction.

## Detail levels and APIs

- SUMMARY is the existing compact library row.
- STANDARD contains rankings, strategy/method and fold summaries, regime summaries, scores, benchmarks, and artifact references. It is the default detail view.
- FULL is an explicit normalized JSON record containing the artifact dictionary. It excludes transient calculation structures.

`GET /api/research/:runId` defaults to STANDARD. `?detail=full` is required for FULL. `GET /api/research/:runId/summary` returns SUMMARY and `GET /api/research/:runId/artifacts/:artifactId` verifies and returns one artifact without rerunning research. Summary, manifest, standard, and full JSON exports remain available. Metadata-only filesystem reads make SUMMARY and STANDARD genuinely lazy after restarts.

## Integrity and reproducibility

Each artifact carries `veyrix-artifact-v1`, its type, content hash, and byte size. Reads recompute the artifact hash. The normalized root fingerprint hashes the manifest fingerprint, a normalized summary (excluding access, persistence, size, and self-referential fingerprint fields), and the sorted list of artifact IDs/content hashes. Consequently object key order and artifact insertion order do not change identity, while a material artifact change does.

V1 records are not silently converted. They are treated as legacy and safely missed so research can be recomputed into V2. Live paper state is never read or mutated by normalization.

## Measured representative 180D result

On the local production build, an all-strategy 180D run measured:

- legacy-equivalent detailed arena: approximately 91.2 MB
- SUMMARY data: 883 bytes; measured HTTP response: 1,163 bytes
- STANDARD data: 509,843 bytes; measured HTTP response: 510,228 bytes
- FULL normalized data: 9,873,697 bytes; measured HTTP response: 9,873,973 bytes
- filesystem storage: 9,774,204 bytes across 1,405 artifacts plus metadata
- reduction from the V0.13 result: approximately 89.2%
- SUMMARY metadata-only store request: 283 ms
- STANDARD metadata-only store request: 528 ms
- FULL normalized serialization/request: 43.71 s
- lazy benchmark artifact request: 28 ms (840-byte response)
- memory-hit research request: 567 ms after final integrity validation (an earlier warm measurement was 148 ms)
- filesystem store-hit research request: 5.65 s
- cold research request: 167.13 s, including Coinbase retrieval, analysis, normalization, hashing, and persistence; a compute run with warm historical data took 25.69 s

Times are machine-, network-, and dataset-dependent. The payload target was met; STANDARD is below 2 MB, though its initial measured request exceeded the aspirational two-second target. FULL remains explicit because hashing and serializing thousands of retained artifacts is intentionally expensive.

## Limitations

Filesystem storage is optional and not durable on ephemeral serverless instances. Deduplication is within a run, not across runs. FULL export retains all selected artifacts and can still be several megabytes. The record metadata currently indexes many small artifact files; object storage or a blob/index adapter is a natural future fit. Historical simulation remains subject to Coinbase coverage and the existing modeling assumptions, and does not predict future performance.
